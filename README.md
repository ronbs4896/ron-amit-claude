# ron-amit-claude

דף נחיתה לקורס הדיגיטלי של עמית ליטמן: בניית סוכן AI לשירות לקוחות בוואטסאפ ובאינסטגרם.
249 ש״ח + מע״מ במקום 997.

הכל נמצא בקובץ אחד: `index.html`. אין תלויות ואין שלב build, פשוט פותחים אותו בדפדפן או מעלים לאירוח.

## מה צריך לערוך לפני שמעלים

### 1. בלוק ההגדרות (בתחתית הקובץ, בתוך `<script>`)

```js
const CONFIG = {
    CHECKOUT_URL: '#',                       // קישור התשלום. חובה.
    DEADLINE: '2026-09-01T23:59:00+03:00',   // מתי מחיר ההשקה נסגר
    HERO_VIDEO: '',                          // יוטיוב / וימאו / mp4. ריק = הנגן לא לחיץ
    TESTIMONIAL_VIDEOS: ['', '', '', ''],    // סרטוני עדויות לפי סדר הכרטיסים
    SHOW_LIVE_SOCIAL: true,                  // "17 צופים עכשיו" + פופאפ רכישות
};
```

`CHECKOUT_URL` — כבר מחווט ללינק Morning. כל כפתורי ה-CTA פותחים **פופ-אפ
הרשמה** (שם, טלפון, מייל, אישור תקנון — הכל חובה), ורק טופס תקין ממשיך
לדף התשלום. `LEAD_WEBHOOK_URL` — מחווט ל-Webhook של Make שמזרים לרב מסר
(ראה סעיף "רב מסר" למטה); ריק = הליד נשמר רק ב-localStorage.
אצל ספק הסליקה יש להגדיר את `thanks.html` ככתובת ההצלחה (success redirect).

`SHOW_LIVE_SOCIAL` שולט על מונה הצופים ("17 צופים עכשיו") ועל מונה הכרטיסים
היורד. פופ-אפ הרכישות הוסר. `false` מכבה את שניהם.

חפש `✏️` בקובץ. כל מופע מסמן טקסט או תמונה שצריך להחליף בתוכן אמיתי,
בעיקר בסקשן של עמית ובכרטיסי הדוגמה של הוואטסאפ.

## צבעים ורצועות

הרקעים אחידים, בלי גרדיאנטים. כל סקשן הוא רצועה בצבע מלא, ושתי רצועות מתחלפות
לסירוגין עם קו דק ביניהן, כדי שהחלוקה בין הסקשנים תהיה ברורה.

```css
--bg:      #0c1a23;   /* רצועה בסיסית */
--bg-alt:  #112935;   /* רצועה מתחלפת */
--bg-deep: #070f15;   /* סרגל עליון, כרטיס המחיר, פוטר */
--bg-card: #17303d;   /* כרטיסים */
```

בפועל: `<section class="section band">` או `class="section band-alt">`.
כדי לחזק או להחליש את ההפרדה, מספיק לשנות את `--bg-alt` ואת `--line`.
מעל כל סקשן יש תווית קטנה (`.eyebrow`) שמסמנת את הנושא.

## תגיות (Badges)

גיאומטריה אחת לכל התגיות בדף, והווריאנט קובע רק צבע:
`padding: 6px 14px`, `radius: 999px`, `12.5px/700`, מסגרת 1px.

```html
<span class="badge badge-success"><span class="b-dot"></span>טקסט</span>
```

| ווריאנט | מתי משתמשים |
|---|---|
| `badge-primary` | מילוי ירוק מלא. הדגשה יחידה במסך, לא יותר מאחת |
| `badge-secondary` | תווית ניטרלית בלי משמעות סטטוס |
| `badge-outline` | תווית שקטה. זה מה שה-`eyebrow` מעל כל סקשן משתמש בו |
| `badge-destructive` | אזהרה, אובדן, מה שהמשתמש מפסיד |
| `badge-success` | תוצאה חיובית, מה שהסוכן השיג |
| `badge-warning` | מחסור וזמן שנגמר |
| `badge-info` | מידע ניטרלי, בלי צבע רגשי |

גדלים: `badge-sm` (10.5px) ו-`badge-lg` (13px). נקודת סטטוס: `<span class="b-dot">`,
יורשת את צבע הטקסט. `pulse-dot` נשארת אדומה בכוונה גם בתוך תגית ירוקה, כי היא
מסמנת דחיפות ולא סטטוס.

על רקע כהה הווריאנטים הם **טונאליים** (מילוי שקוף על הרקע) ולא צבע רווי מלא,
שגורם לזוהר. היוצא מן הכלל הוא `badge-primary` ותגית המחיר בזהב, שתיהן עוגן
ויזואלי מכוון. כל שבעת הווריאנטים נבדקו מול ארבעת צבעי הרצועות ועוברים
WCAG AA לטקסט קטן, הנמוך ביותר 5.97:1.

הסימולטור האינטראקטיבי עבר לדף המכירה, לסקשן ההדגמה, והחליף שם את

בתחתית הקובץ יש `CONFIG` משלו:

## תקנון

התקנון יושב במודאל בדף הראשי (נפתח מהפוטר ומהצ'קבוקס שבפופ-אפ), עם פרטי
אר-בי-אס דיגיטל (ח.פ. 516866878) ומדיניות מחמירה: החזר רק עד 14 יום
**וכל עוד לא נפתחו התכנים**; צפייה בשיעור = רכישה סופית. סעיף קניין רוחני
עם פיצוי מוסכם של 50,000 ש״ח להפרה. הבטחת "14 יום להתחרט" הוסרה מהדף
כדי שלא תסתור את התקנון. זו טיוטה, לא ייעוץ משפטי — חובה עו״ד לפני פרסום.

אותו נוסח בדיוק יושב גם בעמוד עצמאי, `takanon.html`, שנפתח בכתובת קבועה
`/takanon`. זה מה שנותנים לגורם חיצוני שמבקש קישור לתקנון: ספק הסליקה,
מטא, גוגל, או שורת הביו באינסטגרם. לעמוד יש תוכן עניינים עם עוגנים, כך
ש-`/takanon#refund` נוחת ישירות על סעיף הביטול, ויש לו עיצוב הדפסה
שמאפשר לשמור אותו כ-PDF. המודאל בדף המכירה נשאר, כי הוא לא מוציא את
הגולש מהמשפך, ובתחתיתו יש קישור לעמוד המלא.

**כשמעדכנים את התקנון צריך לעדכן את שני המקומות** — המודאל ב-`index.html`
והעמוד ב-`takanon.html`. הנוסח המשפטי זהה מילה במילה, וכך זה צריך להישאר.

## הפונט

Birzia כבר נמצא בריפו בארבעה משקלים, בשני פורמטים: `woff2` לכל דפדפן מודרני
ו-`woff` כגיבוי. הקבצים חייבים להישאר **ליד `index.html`**, בשמות שלהם.

```
Birzia-Light.woff2 / .woff     משקל 300
Birzia-Medium.woff2 / .woff    משקל 400-500
Birzia-Bold.woff2 / .woff      משקל 600-700
Birzia-Black.woff2 / .woff     משקל 800-900
```

לכל `@font-face` יש גם `local()`, כלומר מי שהפונט מותקן אצלו במחשב יראה אותו
בלי להוריד כלום. הדף טוען מראש את משקל 900, שהוא הנפוץ ביותר, כדי שלא יהיה
הבזק של Heebo בטעינה.

**אם פותחים את הקובץ בלחיצה כפולה** (כתובת `file://`) הקונסול יראה שגיאת CORS
על ה-preload. זה מגבלה של הפרוטוקול ולא באג, והפונט עצמו נטען כרגיל. בשרת
אמיתי זה נקי, ובדקתי שאין הורדה כפולה.

**רישוי:** רישיון דסקטופ בדרך כלל לא מתיר הטמעה באתר. שווה לוודא מול מי
שקנית שיש כיסוי לשימוש ווב לפני שזה עולה לאוויר.

## המספרים שבדף

החישוב בכל הדף אחיד ומבוסס על 40 ש״ח לשעה:

## רב מסר (לידים ורוכשים)

שני הדפים שולחים ל-`/api/lead`, פונקציית Serverless שרצה על Vercel מתוך
`api/lead.js`:

- דף המכירה, אחרי מילוי תקין של פופ-אפ ההרשמה: `stage: "lead"` ← רשימת ה-hotlist
- דף התודה, פעם אחת לדפדפן: `stage: "purchase"` ← רשימת הרוכשים, **ומחיקה מה-hotlist**,
  כך שרוכשים לא ממשיכים לקבל מיילים של "בוא תקנה"

### איך זה מגיע לרב מסר

הפונקציה מוסרת ל-Webhook של תרחיש Make בשם
**"קורס סוכני AI — לידים ורוכשים לרב מסר"** (מזהה 9679108, פעיל), ושם ראוטר
מפריד בין שני המסלולים:

| מסלול | תנאי | מה קורה |
|---|---|---|
| ליד | יש מייל ו-`stage` שאינו `purchase` | נרשם לרשימה **Agents AI - Digital Product** (114908) |
| רכישה | יש מייל ו-`stage = purchase` | נרשם לרשימה **Agents AI - רוכשים** (114990), ואז חיפוש הכתובת ב-hotlist והוצאתה משם |

תנאי הליד מנוסח כ"כל מה שאינו רכישה" בכוונה: פנייה שתגיע בלי `stage` תיכנס
כליד במקום להיבלע בשקט. שלב החיפוש נחוץ כי האפליקציה מסירה מנוי לפי מזהה
ולא לפי כתובת מייל.

**האפליקציה הנכונה ב-Make היא Responder.live** ולא "Rav Messer / Responder"
הישנה. הראשונה מבקשת שדה אחד, User Token; השנייה מבקשת זוג מפתחות שהתמיכה
מנפיקה, וזה מה שתקע אותנו. את הטוקן לוקחים מרב מסר: הגדרות ← חיבורים
חיצוניים (API).

### מעקב מקורות (UTM ו-ref)

הדף קורא מה-URL את `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`,
`utm_term`, `ref` ואת מזהי הקליק של הפרסום (`fbclid`, `gclid`, `ttclid`),
שומר אותם ב-localStorage בביקור הראשון ולא דורס אחר כך. כך גולש שהגיע
ממודעה, יצא, וחזר ישירות כעבור יומיים עדיין נזקף לאותה מודעה. אותם ערכים
נוסעים גם עם הליד וגם עם דיווח הרכישה מדף התודה.

ברב מסר הוקמו שדות מותאמים ברמת החשבון (זמינים בכל הרשימות), ותרחיש Make
ממפה אליהם:

| שדה | מזהה |
|---|---|
| `utm_source` | 108979 |
| `utm_medium` | 108980 |
| `utm_campaign` | 108981 |
| `utm_content` | 108982 |
| `utm_term` | 108983 |
| `ref` | 108984 |

מבנה קישור: `https://ron-amit-claude.vercel.app/?utm_source=instagram&utm_medium=story&utm_campaign=agents-ai&ref=amit`.

עקביים בין הערוצים, אחרת הפילוח ברב מסר מתפזר.

### המסלול הישיר (עדיין לא פעיל)

הפונקציה יודעת גם לדבר עם `api.responder.co.il` בעצמה, ונופלת לשם אם Make
לא זמין. זה דורש consumer key משלנו, שרב מסר טרם הנפיקו. מה שנבדק:
כותרת בלי `c_key` מוחזרת עם 400 "Invalid consumer key", ואילו `c_key` שאינו
מוכר גורם ל-500 עם גוף ריק — וה-Client ID ממסך "מפתח כללי לחשבון" מתנהג
בדיוק כמו מפתח מומצא. כלומר הוא שייך למערכת אחרת של רב מסר.

`/api/lead?selftest=1` (מוגן מאחורי `RAV_SELFTEST=1`) מריץ את כל וריאציות
האימות מול ה-API הישיר ומחזיר את התשובה של רב מסר לכל אחת, וגם את הרשימות
בחשבון עם המזהים שלהן כשהחיבור מצליח.

משתני סביבה (Vercel ← Settings ← Environment Variables):

| משתנה | למה |
|---|---|
| `MAKE_WEBHOOK_URL` | ה-Webhook של התרחיש. יש ברירת מחדל בקוד |
| `RAV_U_KEY` / `RAV_U_SECRET` | זוג החשבון מהתמיכה (03-7177777) |
| `RAV_CLIENT_ID` / `RAV_CLIENT_SECRET` / `RAV_USER_TOKEN` | ממסך "מפתח כללי לחשבון" |
| `RAV_LIST_HOTLIST` / `RAV_LIST_BUYERS` | מזהי הרשימות, למסלול הישיר |
| `RAV_SELFTEST` | `1` בזמן הגדרה בלבד |

דיבוג: הלוגים של הפונקציה נמצאים ב-Vercel תחת Deployments ← Functions.

## מטא: פיקסל ו-Conversions API

הפיקסל `1410625827632523` יושב בשני הדפים ויורה ארבעה אירועים:

| אירוע | מתי | ערך |
|---|---|---|
| `PageView` | טעינת דף | — |
| `InitiateCheckout` | נגיעה ראשונה בטופס, או פתיחת הפופ-אפ | 293.82 ILS |
| `Lead` | שליחת טופס תקין, רגע לפני המעבר לתשלום | 293.82 ILS |
| `Purchase` | דף התודה, פעם אחת לדפדפן | 293.82 ILS |

`InitiateCheckout` ו-`Purchase` מוגנים כך שלא יורים פעמיים: הראשון בדגל
בזיכרון הדף, השני ב-`localStorage` (`rbs_purchase_done`), כדי שרענון של דף
התודה לא ייצור רכישה נוספת. `fbq('init', …)` נקרא שוב עם המייל, הטלפון והשם
לפני `Lead` ו-`Purchase` — זה ה-Advanced Matching, שמעלה את אחוז ההתאמה.

### הצד השרתי (CAPI)

חוסמי פרסומות, ‎iOS ומחיקת קוקיז בולעים חלק מהאירועים של הדפדפן. לכן
`api/lead.js` שולח את אותם `Lead` ו-`Purchase` גם ישירות למטא, מהשרת:

* אותו `event_id` נשלח משני הצדדים (`lead_…` ו-`purch_…`), ומטא ממזגת את
  שני העותקים לאירוע אחד. בלי זה כל המרה הייתה נספרת פעמיים.
* הפרטים האישיים נשלחים מוצפנים ב-SHA-256 בלבד, אחרי נרמול כפי שמטא דורשת:
  מייל באותיות קטנות, טלפון עם קידומת מדינה בלי `+` (`972…` או `1…`),
  שם פרטי ושם משפחה בנפרד, קוד מדינה.
* נשלחים גם `_fbp` ו-`_fbc` (קוקיז של הפיקסל, ה-`_fbc` נבנה מ-`fbclid`
  כשהקוקי עוד לא נכתב), כתובת ה-IP וה-User Agent — כל אלה משפרים את ההתאמה.
* כישלון מול מטא לא מפיל את הליד. הוא נרשם בלוג ותו לא.

הגדרה חד-פעמית:

1. Events Manager ← Data Sources ← הפיקסל ← Settings ← Conversions API ←
   **Generate access token**
2. Vercel ← Settings ← Environment Variables ← `META_CAPI_TOKEN` = הטוקן.
   Redeploy.
3. לבדיקה: Events Manager ← Test Events, מעתיקים את קוד הבדיקה למשתנה
   `META_TEST_EVENT_CODE`, ממלאים טופס באתר, ורואים את `Lead` מגיע פעמיים —
   Browser ו-Server — עם סימון Deduplicated. אחר כך מוחקים את המשתנה.

| משתנה | למה |
|---|---|
| `META_CAPI_TOKEN` | חובה. בלעדיו השרת פשוט מדלג על השליחה |
| `META_PIXEL_ID` | ברירת מחדל: הפיקסל שבדפים |
| `META_TEST_EVENT_CODE` | זמני, לבדיקה במסך Test Events בלבד |

## Grow: סליקה עם Webhook לשרת

כשהסליקה עוברת ל-Grow, השרת הופך למקור האמת לרכישות במקום דף התודה.
`api/grow.js` מקבל קריאה מ-Grow אחרי כל עסקה — אשראי, ביט, Apple Pay,
Google Pay, PayBox או העברה בנקאית, כולם באותו Webhook — ומבצע שני
דברים: שולח `Purchase` למטא דרך ה-CAPI, ומעביר את הרוכש ברב מסר מרשימת
ה-hotlist לרשימת הרוכשים.

זה סוגר שלושה חורים שדף התודה לבדו לא סוגר: מי שסגר את הדפדפן לפני
שחזר לאתר, מי ששילם ממכשיר אחר מזה שבו מילא את הטופס, ומי שחוסם את
הפיקסל.

### מניעת ספירה כפולה

שני הצדדים חייבים לשלוח את אותו `event_id`, אחרת מטא סופרת שתי רכישות
על עסקה אחת. המזהה הוא `grow_<transactionCode>`:

* השרת לוקח את `transactionCode` מגוף ה-Webhook.
* דף התודה לוקח אותו מכתובת ההפניה (`transactionCode`, `asmachta`
  ווריאציות נוספות).
* **אם אין מספר עסקה בכתובת, דף התודה שותק לגמרי** ונותן לשרת לדווח
  לבדו. עדיף אירוע אחד מהשרת מאשר שניים עם מזהים שונים.

המתג נמצא ב-`thanks.html`, בשדה `CHECKOUT_PROVIDER`. כל עוד הוא
`'morning'` ההתנהגות היא הישנה: דף התודה יורה `Purchase` ושולח את
הרוכש ל-`/api/lead`. ברגע שמעבירים אותו ל-`'grow'`, ה-Webhook לוקח
אחריות על שניהם.

### הגדרה

1. Vercel ← Environment Variables ← `GROW_URL_TOKEN` = מחרוזת אקראית
   ארוכה שאתה ממציא.
2. אצל Grow, כתובת ה-Webhook:
   `https://ron-amit-claude.vercel.app/api/grow?t=<אותה מחרוזת>`
3. אם Grow מנפיק `webhookKey` משלו, שמים אותו גם ב-`GROW_WEBHOOK_KEY`.
4. `GROW_LEARN=1` בעסקה הראשונה, ואז Vercel ← Functions ← Logs מציג את
   כל שמות השדות שהגיעו בפועל (בלי הערכים האישיים, רק אורכים). אחרי
   שנועלים את השמות — מוחקים את המשתנה.
5. כתובת ההפניה אחרי תשלום מוצלח: `https://ron-amit-claude.vercel.app/thanks`

**בלי `GROW_URL_TOKEN` או `GROW_WEBHOOK_KEY` הפונקציה מחזירה 401 ולא
עושה כלום.** זה מכוון: כתובת פתוחה מאפשרת לכל מי שימצא אותה להזריק
רכישות מזויפות לפיקסל ולרשימת הדיוור.

| משתנה | למה |
|---|---|
| `GROW_URL_TOKEN` | סוד בכתובת ה-Webhook. חובה (או `GROW_WEBHOOK_KEY`) |
| `GROW_WEBHOOK_KEY` | ה-`webhookKey` ש-Grow שולח בגוף, אם יש |
| `GROW_LEARN` | `1` בעסקה הראשונה בלבד |

### מה עוד לא נעול

שמות השדות (`transactionCode`, `statusCode`, `paymentSum`, `payerEmail`,
`payerPhone`, `fullName`) נלקחו מהתיעוד של Grow, אבל התיעוד עצמו לא היה
נגיש מסביבת הפיתוח. לכן הקוד מקבל כמה וריאציות לכל שדה, ו-`GROW_LEARN`
נועד לאמת מול עסקה אמיתית. עסקה שאינה `statusCode=2`, וכל זיכוי, נרשמת
בלוג ולא נספרת.

אם נעביר את `_fbp` ו-`_fbc` כשדות מותאמים בקישור התשלום, הם יחזרו
ב-Webhook (`cField1`/`cField2`) והקוד כבר יודע לקרוא אותם. זה משפר את
איכות ההתאמה, אבל מטא מתאימה גם בלעדיהם לפי המייל והטלפון המוצפנים.
